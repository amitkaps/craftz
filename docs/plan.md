# Plan

craftz 0.3.0 is on npm, and its docs are live at [craftz.amitkaps.com](https://craftz.amitkaps.com). What each release changed is in its [notes on GitHub](https://github.com/amitkaps/craftz/releases). This plan says what's next, in order, and what works now. [The design](design.md) is the whole of what craftz becomes. Each repository moves to a release in its own pull request, which its own plan tracks.

## Next, in order

Every repository is on 0.3.0. craftz started as a repository that checked the others from a laptop, and it now works as a package. 0.4.0 is a breaking release, so it carries every change that touches each repository, and the repositories change once. It still waits for enough feedback to release.

- [x] **Errors, warnings and notes**, as [the design](design.md#errors-warnings-and-notes) has them. Since each repository checks itself, a hold kept in craftz costs a craftz release to add or drop, so holds move into each repository's `package.json`. Rules a tool can block are marked holdable. `check` notes a newer craftz and a graduated beta, and the upgrade fix moves base's two holds into base.
- [x] **A `tsconfig.json` the package ships.** A repository's `tsconfig.json` extends `@amitkaps/craftz/tsconfig.json` and says only what to include, as `vite.config.ts` uses `craftz()`, so every option lives in craftz. It checks JavaScript too, and keeps to the TypeScript Node runs as it is. prose and pagez write out their constructors' parameter properties, and prose and amitkaps fix what checking their JavaScript finds. Base holds the rule, since SvelteKit needs its own `types` and `checkJs` off.
- [ ] **Yes-or-no rules, and no edits by line**, as [the design](design.md#no-edits-by-line) has them. `cloudflare-wrangler` is gone, and base holds `cloudflare-config` instead. `worker()`, from `@amitkaps/craftz/cloudflare`, sets a Worker's date and addresses, and `cloudflare-worker` only looks for it, in place of `cloudflare-addresses` and `cloudflare-date`. cf and Cloudflare's plugin both load a config that imports it. CI, pnpm's settings, the editor's and a package's release files are craftz's, checked word for word against [reference/](../reference/README.md) and written whole, so what a repository adds goes in `verify`. An app adds Svelte's editor settings. Still to do: `craftz()` takes on publint, declarations, platform and a site's folder. The fixes for old layouts are deleted.
- [ ] **Move the shared tools.** `pnpm bump` moves Vite+ to 1.4.0, wrangler to 4.152.0 and pnpm to 12.15.0, once Vite+ 1.4.0 is past pnpm's one-day wait on 2026-10-24. None of them unblocks an item below, but each brings fixes. Vite+ 1.4.0's newer oxlint and oxfmt can flag code that passed before, so read each repository's align pull request for formatting changes.
- [ ] **Move the betas to a matching pair.** cf goes to `1.0.0-beta.20` and the Vite plugin to `2.0.0-beta.v.3`, since both use `@cloudflare/config` 0.27.0. The plugin's `v.4` uses 0.28.0, which no cf build has yet. Neither beta lets the app move to cf.
- [ ] **Raise Node's floor to 26.12.1.** 26.12.1 is Node's October 2026 security release, so the floor is a general safety fix, and cf beta.20 needs 26.12.0 anyway. [`versions-node`](rules.md#versions-node) asks for `>=26.12.1` in `engines` and `devEngines`, and `new` says so in a package's README. A higher floor breaks a package's users on an older Node, which 0.4.0 can carry.
- [ ] **Release 0.4.0.** Its notes say what each repository changes, and `pnpm align` moves every repository to it.

## Where it is

- **Each repository checks itself.** Its CI runs `craftz check` against the craftz it installs, so nothing checks it from outside. What needs a login stays on the laptop: `craftz settings --check`, `craftz status`, and `pnpm align --local` for every repository at once.
- **Exact versions.** Every shared tool and craftz are pinned exactly, in one list, the reference's `package.json`, so a repository runs what it names.
- **`craftz upgrade`.** One command moves a repository to the latest craftz and runs that version's fix, and align runs its steps in a clone of each repository.
- **The rules, checked and fixed.** [The rules](rules.md) are worded once, and their checks and fixes are in [src/](../src/), against the files in [reference/](../reference/README.md). `craftz rules`, `check` and `fix` run them from the installed version, and a second `fix` changes nothing. Every `verify` runs `pnpm craftz check`, so each pull request is checked against the craftz it installs. craftz checks itself from source, since the version it installs can't hold the rules it's changing. Its tests install the package `pnpm pack` writes, as a repository would, so a file the package leaves out fails a test here. A repository holds a rule a tool blocks in its own `package.json`, which `check` prints as a warning, and `check` notes a newer craftz.
- **GitHub's settings.** `craftz settings` writes only what has drifted and reads it back, with `--check` to only read. A package's ruleset requires `label` next to `ci`.
- **One toolchain.** `craftz()` sets every repository's `fmt` and `lint`, and fails a config that sets either differently. Its values are stated once, and `toolchain-craftz`'s fix reads them to take each out of a config. A static site names its own folder as Vite's `publicDir`, and `craftz()` never guesses one. `craftz deploy` runs cf, or wrangler for an app cf can't build yet.
- **Pull requests.** `pnpm pr` and `pnpm gone` run craftz's commands, in place of the scripts every repository copied. `pr` starts where the title says, and stops when the branch has nothing new for `main`. A package's label is checked by `label.yml`, so a pull request runs `verify` once. `gone` removes a merged branch's worktree.
- **What's live.** `craftz status` reads CI on `main`, the open pull requests, npm's version against `package.json` on `main`, the latest release, and a site's build, addresses and audience, on cf or wrangler.
- **Releases.** The release workflow stages a version on npm and tags it once approved, and each release's notes say what to change when a repository moves. `pnpm bump` moves the reference's versions before a release. After it, `pnpm align` runs `craftz upgrade` in a clone of each repository, so a change reaches the others only once it's released. `craftz new` starts a repository that passes the rules, from any folder with `pnpm dlx`. `craftz release` opens a package's release from its own folder. align and bump are this repository's own scripts, for whoever keeps the repositories, and the package doesn't ship them.
- **The repositories.** The public ones carry the topic `craftz`, which is how align finds them.

## Later

- The old repository retires. The one that kept the rules before craftz is archived with its history, and its site redirects to craftz's, for the links outside these repositories. Nothing in these repositories links to it, and every `AGENTS.md` links to craftz.
- The beta packages that [`versions-beta`](rules.md#versions-beta) names move to their releases when they graduate, which align reports.
- The app moves to cf when SvelteKit's adapter writes cf's Build Output, and wrangler leaves the reference with it.
- The app moves to TypeScript 7 when svelte-check's peer range takes it.
- A site's `vp check` loads Cloudflare's plugin, though only `vp build` uses it. Vite+ loads the whole config for `fmt` and `lint` too, and the plugin takes a second to import, most of it compiling its 4 MB bundle and miniflare's 6 MB one. So a site checks in about 7 seconds where a package takes under 3, and three sites are most of craftz's test time. A config can't load it only to build, since `vp check` passes it `command: "build"`, as `vp build` does. It waits for Vite+ to tell a check from a build, or for the plugin to load less until it's used.
- A size budget for packages a browser loads, measured as markz's `pnpm size` does: bundled, minified and gzipped. It waits for a second package that needs one, since a Node tool like craftz pays for its install, not its bundle. Speed stays each package's own, since what it times differs.

## Open questions

- **Where axes meet badly.** A package in a private repository can't publish with provenance, and only `new` says so. A private repository's rulesets need a paid GitHub plan, which this account has. Each could be a warning, once a repository is in that position and warnings exist. A private npm package would add a value to the publish axis, and none is needed yet.

- **Browser code Vite doesn't build.** prose's and pagez's page scripts and styles are copied as they're written, so [`toolchain-browsers`](rules.md#toolchain-browsers) doesn't reach them, and nothing stops them using a feature past a floor. A Baseline lint that reads the same list would, once oxlint has one. Until then, check a new feature's support by hand.

  prose's `built` plugin runs oxfmt, which only formats. Lowering syntax is in reach: `vite-plus` exports `transformWithOxc` for JS, and Lightning CSS's `transform({ targets })` does CSS, as a devDependency. But at today's floors there's little to lower, and Oxc's lowering can add `require` of its runtime helpers, which a page script can't load. An API past a floor, like `::highlight()`, can't be lowered at all, so the lint is the part that matters.

- **Keeping the docs fresh.** The docs are checked for their files, not their sections, and that stays. What goes stale is what they say, like `development.md` describing a setting the rules have moved past, and a check can't tell. One cheap signal is when each doc last changed beside when the code did, so a doc untouched through many changes stands out, without failing anything. That's a note, so it can come in any release after 0.4.0, since a new note breaks nothing.
