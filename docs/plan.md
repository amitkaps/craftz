# Plan

craftz 0.16.0 is on npm, and its docs are live at [craftz.amitkaps.com](https://craftz.amitkaps.com). What each release changed is in its [notes on GitHub](https://github.com/amitkaps/craftz/releases). This plan says what's next, in order, and what works now. [The design](design.md) is the whole of what craftz becomes.

This is a package's plan, of what craftz itself does next. Each repository moves to a release in its own pull request, which its own plan tracks, so this plan never lists those moves.

## Next, in order

- [ ] `craftz status` notes an `e2e` run over its two-minute budget, as it notes a `verify` over ten seconds. [The rules](rules.md#ci) already say it does.

## Where it is

- **Each repository checks itself.** Its CI runs `craftz check` against the craftz it installs. What needs a login stays on the laptop: `craftz settings --check`, `craftz status`, and `pnpm align --local` for every repository at once. craftz checks itself from source, and its tests install the package `pnpm pack` writes, so a file the package leaves out fails a test.
- **Exact versions.** Every shared tool and craftz are pinned exactly in the reference's `package.json`. cf is a beta that no repository installs, and craftz reads the Workers' compatibility date from the workerd it depends on. Node's floor is 26.13.0, the first LTS, and pnpm is 12.16.1. `@playwright/test` is held to the version whose Chromium the Claude Code cloud image ships, which `pnpm bump` leaves.
- **The rules, checked and fixed.** [The rules](rules.md) are worded once, and each check and fix is in [src/rules/](../src/rules/), one module for each part, against the files in [reference/](../reference/README.md). `craftz rules`, `check` and `fix` run them from the installed version, and a second `fix` changes nothing. A repository holds a rule a tool blocks in its own `package.json`, which `check` prints as a warning. A test per shape ([fixes.ts](../tests/fixes.ts)) breaks a new repository one file or key at a time and fails any fix that leaves its check drifting, bar the gaps it lists.
- **Practice.** Ten principles are a part of [the rules](rules.md), three before the code, four while writing it and three after it runs. Each repository's `lessons.md` groups its lessons under them, and `craftz check` holds every link into the rules to an id the installed craftz has.
- **One way in craftz's own code.** A whole-repository audit left one `gh`, one command runner, one reader for `package.json` and JSON, one `isCraftz`, one `isPrerelease`, one `tmp` for the tests and one `flagged` for flags. A command takes a temporary folder from one module, and a test fails a `mkdtemp` anywhere else in `src/`.
- **One toolchain.** Each config writes out its `fmt` and `lint`, a `tsconfig.json` its compiler options, and a package its publint, types and platform. A site Vite bundles writes out its browsers. A static site is built by Vite, SvelteKit's static adapter or `prose build`, and its `cloudflare.config.ts` is cf's own format, naming the folder and writing out the Worker's date and addresses. `craftz deploy` uploads it, or runs wrangler for an app.
- **Cloud sessions.** Claude Code's settings and two hooks are craftz's, the same in every repository and the same on a laptop and in the cloud. The session-start hook runs `pnpm install`, then installs Chromium's headless shell where a repository has Playwright. The cloud image ships that shell, so it downloads nothing. [cloud-setup.sh](../reference/cloud-setup.sh) is pasted once into an environment and installs the reference's Node and pnpm. `pnpm pr`, `gone`, `status` and `release` talk to GitHub over REST, which a cloud session's proxy allows. `craftz shot <url> <file.png>` saves a page as a PNG with the repository's Playwright. Cross-repository work, `align`, `new` and `bump`, stays on the laptop.
- **Files craftz owns.** CI, pnpm's settings, the editor's, Claude Code's and a package's release files are checked word for word against [reference/](../reference/README.md) and written whole, so what a repository adds goes in `verify`.
- **GitHub's settings.** `craftz settings` writes only what has drifted and reads it back, with `--check` to only read. A package's ruleset requires `label` next to `ci`.
- **A parallel `verify`.** It runs `check`, `test`, `build` and `site` side by side, so it takes as long as the slowest. It has a 10-second budget, which `status` notes when it's over, naming the slowest step. craftz's own is about 20 seconds. A repository with browser checks runs them as `test:e2e` in an `e2e` workflow, with a two-minute budget the rules state.
- **Pull requests.** `pnpm pr` takes the working tree to a pull request that merges itself once CI passes, and `--wait` waits for the merge. `pnpm gone` merges a finished one, deletes what merged and ends on `main`, pulled. Both write `outline.md`, and a failed step stops them with one `craftz: error:` line.
- **What agents read.** Every `AGENTS.md` opens with the same sections, word for word from the [reference](../reference/AGENTS.md). They say to read the rules by part, with `craftz rules <part>`, a fifth of the whole. They also say to run `pnpm gone` before a change, that `pnpm pr` runs `verify`, to look at a page with `pnpm craftz shot <url> <file.png>`, and where `outline.md` is, which they open if they want it. It isn't imported, since agents never read it unprompted. Across 21 sessions on craftz and visframe, an agent found the same files with the outline loaded, left out or named in a bullet, so the headers stay as they are.
- **The commands, stated once.** Each command opens its section of [usage](usage.md) with an id, and `craftz help` prints from there. A test fails if cli.ts runs a command usage doesn't state, or the other way, and the README links each one.
- **What's live.** `craftz status` reads CI, pull requests, npm, the latest release, and a site's build, addresses and audience. `--timing` says what the last pull requests took and why slow ones were slow, from GitHub's own record of their runs and commits. `craftz deps` weighs an install by direct dependency.
- **Releases.** The release workflow stages a version on npm and tags it once approved. `pnpm bump` moves the reference's versions, and `pnpm align` runs `craftz upgrade` in a clone of each repository, so a change reaches the others only once it's released. `craftz new` starts a repository that passes the rules. `craftz release` opens a package's release once the plan's summary names the version and no step is ticked. Every plan's steps are tasks, which [`docs-plan`](rules.md#docs-plan) checks. align and bump are this repository's own scripts, and the package doesn't ship them.
- **The repositories.** The public ones carry the topic `craftz`, which is how align finds them.

## Later

- Each rule's fix in [src/rules/](../src/rules/) is written beside its check, and the two could disagree. [fixes.ts](../tests/fixes.ts) breaks a new repository of each shape one way at a time, by deleting a file, emptying it or dropping a key, and fails any rule whose fix leaves its check drifting. It found six gaps. Two closed, an empty doc and a missing `tsconfig.json`. Four are left by hand and listed in the test: a README, a deleted `vite.config.ts`, the `vite-plus` dependency and a `build` script that is only `vp build`. It breaks files and keys, not values, so a fix that mishandles a wrong value is for [rules.test.ts](../tests/rules.test.ts). Deriving every fix from its check would be a rewrite of about 1,500 lines for gaps that small, so it waits until that test finds many.
- `worker.ts` reads `wrangler.toml` with regexes, and `directory` matches under any table. A real parser or dropping `wrangler.toml` fixes it, and the choice depends on when the app leaves wrangler.
- Cloudflare's error `[12040]` is matched in a message in `settings.ts`. A small client with typed errors would hold every code's meaning in one place.
- `cli.ts` imports every command at startup, though only `new` loads lazily. It waits until startup time is a cost someone feels.
- The beta packages that [`versions-beta`](rules.md#versions-beta) names move to their releases when they graduate, which align reports.
- The app moves to cf when SvelteKit's adapter writes cf's Build Output, and wrangler leaves the reference with it.
- The app moves to TypeScript 7 when svelte-check's peer range takes it.
- A size budget for packages a browser loads, measured as markz's `pnpm size` does: bundled, minified and gzipped. It waits for a second package that needs one, since a Node tool like craftz pays for its install, not its bundle. Speed stays each package's own, since what it times differs.

## Open questions

- **Where axes meet badly.** A package in a private repository can't publish with provenance, and only `new` says so. A private repository's rulesets need a paid GitHub plan, which this account has. Each could be a warning, once a repository is in that position and warnings exist. A private npm package would add a value to the publish axis, and none is needed yet.

- **Browser code Vite doesn't build.** prose's and pagez's page scripts and styles are copied as they're written, so [`toolchain-browsers`](rules.md#toolchain-browsers) doesn't reach them, and nothing stops them using a feature past a floor. A Baseline lint that reads the same list would, once oxlint has one. Until then, check a new feature's support by hand.

  prose's `built` plugin runs oxfmt, which only formats. Lowering syntax is in reach: `vite-plus` exports `transformWithOxc` for JS, and Lightning CSS's `transform({ targets })` does CSS, as a devDependency. But at today's floors there's little to lower, and Oxc's lowering can add `require` of its runtime helpers, which a page script can't load. An API past a floor, like `::highlight()`, can't be lowered at all, so the lint is the part that matters.

- **Keeping the docs fresh.** The docs are checked for their files, not their sections, and that stays. What goes stale is what they say, like `development.md` describing a setting the rules have moved past, and a check can't tell. One cheap signal is when each doc last changed beside when the code did, so a doc untouched through many changes stands out, without failing anything. That's a note, so it can come in any release after 0.4.0, since a new note breaks nothing.
