# Lessons

What setting up the repositories' builds and deploys taught, and then building craftz, for whoever changes them next. Each lesson says what happened and what to do about it. Lessons that belong to one repository stay there.

The first sections are about the tools, what each does that its docs don't say. The rest are about how craftz works: its rules, its fixes, its commands, its tests and its releases. Many were learned before craftz, when one repository kept the rules and copied them into the rest, so some name the scripts it had, like `pnpm drift` and `pnpm new`. The lessons hold for the commands that replaced them.

## pnpm

- **An exact pin with `onFail: error` breaks on every pnpm release.** A newer global pnpm refused to run with `ERR_PNPM_BAD_PM_VERSION`. `onFail: download` makes it fetch and run the pinned version instead. A range would also work, but lets machines run different versions.
- **npm's `latest` for pnpm runs behind its releases.** pnpm 12.13.0 was out on GitHub while `latest` still pointed at 12.11.2. The pin is exact, so the rules can name any published version, whatever `latest` says.
- **pnpm 12.13.0 needs its install script.** Its `pnpm` file is a placeholder the script swaps for the native binary, so an installer that skips scripts runs it through Node, or fails. Install the global pnpm from its GitHub release, as mise's default source does, not from npm.
- **npm's latest and pnpm's wait disagreed for a day.** The survey called a version drift that pnpm's one-day wait wouldn't install yet, so nobody could fix it. The check compares with the reference, not npm, and `pnpm bump` moves the reference with pnpm itself, so the wait is pnpm's rule and not a copy of it.
- **A list of exceptions to the wait needed an edit on every release.** pnpm rewrote `minimumReleaseAgeExclude` on install, in a form `vp check` rejects. The wait is on everywhere with `@amitkaps/*` excluded, a pattern pnpm keeps, so a release changes nothing.
- **align stopped at the first failure, so a run showed one of each repository's problems.** prose failed `upgrade`'s `fix` on its type errors, so the run never reached its fresh lockfile or `verify`'s findings. A step that fails on what's left by hand now leaves it in the list and goes on, so one run says everything.
- **The list of repositories left out three private ones.** It searched without a login, so three private repositories, each with the topic, stayed on 0.1.2 through two releases. It was there so craftz wouldn't name them, but the names only reach the terminal and each repository's own pull request. It searches as `gh` now.
- **A lockfile keeps what nothing installs any more.** esbuild stayed in four repositories' lockfiles, with its platform binaries, as an optional peer of Vite+ once Vite+ moved to Rolldown, and `pnpm dedupe` kept it. A fresh resolve of prose had 238 packages where its lockfile had 345. align now writes the lockfile afresh on every run, so what's stale goes, and the nested packages move within the wait.
- **`bump` left our own markz for review as a new major.** Below 1.0 a minor counts as a major, so markz 0.7.0 was listed rather than taken, though our own numbers only count releases. `update` now takes our own packages at any version, and their notes say what changed.
- **A shorter wait looked like a fix for a blocked release.** prose couldn't take markz 0.7.0, and Vite+ 1.4.0 was a day from the wait's end, so 12 hours looked like it would unblock both. The block was the version check, not the wait, and any number of hours is as arbitrary as pnpm's day. Weigh a wait by what it guards, the libraries nobody reads, and keep the default.
- **A hand pin inside the wait is let in, not refused.** Pinning the Cloudflare betas a day after their release made `pnpm install` add each new package to `minimumReleaseAgeExclude`, and the check of pnpm's settings failed `new.test.ts`. Check `pnpm view <name> time` before pinning a beta. If a pin went in too soon, move it back and restore `pnpm-lock.yaml` from `main`, since the lockfile still holds the rejected versions.
- **Turning the wait back on failed a lockfile that had skipped it.** `pnpm install` passed, but the frozen install CI runs checks each locked version against the wait. Run `pnpm install --frozen-lockfile` locally before pushing a change to these settings.
- **A range checks a floor, not a version.** The rules held every repository to the reference's `^4.151.0`, but a range lets the lockfile hold any 4.x above it, so two repositories could pass and run different versions. Each shared tool, and craftz, is now exact. The reference's catalog, for the tools it didn't install, went too. pnpm 12 writes `catalog:` for a tool a catalog names, and `pnpm update --latest` never moves an entry nothing uses, so bump had to resolve a second list in a scratch project.
- **Some script names never run.** `pnpm deploy`, `audit`, `publish` and `ci` are pnpm's own commands, so a script by one of those names is skipped. That's why the deploy script is `ship`.
- **`npx` refuses to run where `devEngines` names pnpm.** Use `pnpm exec` for an installed tool, and `pnpm dlx` for one that isn't.
- **A candidate run checked the release, not the candidate.** align added the packed craftz, then its fix pinned craftz to its own version, 0.10.0, which npm already had. The install after the fix brought npm's back, so every clone's `verify` ran the old rules on files the new fix had written, and listed drift that wasn't there. `upgrade` adds a tarball again after the fix. When a run's findings read like an older craftz, check which one the clone installed.
- **`pnpm add` doesn't run a repository's `prepare`.** align began a fresh clone with `pnpm add` of the latest craftz, and a later `pnpm install` found nothing to do. So base's `prepare` never generated its Worker's types, and its `fix` failed on the missing file. The clone now installs first, as any fresh clone does.
- **`node_modules` isn't the install.** craftz's read 952 MB, but its install was 502 MB. pnpm keeps each version in `node_modules/.pnpm` after nothing needs it, until a fresh install, so four builds of workerd sat there where one was used. And the lockfile's 234 packages counted builds for other platforms, where 120 were installed. `craftz deps` counts only what the tree reaches on disk, and lists the rest apart.
- **Moving between toolchains needs a fresh lockfile.** A lockfile keeps the optional peers it already resolved, so remove `node_modules` and `pnpm-lock.yaml` before installing.

## Vite+ and TypeScript

- **`vp check` is the whole check.** Type-aware lint with `typeCheck: true` reports compiler errors too, so it replaces `tsc`, with no `typescript` dependency. `vp check --fix` writes the fixes, so there's no `vp fix`, and no separate lint and format steps.
- **A plugin's `config` hook sets what `vp fmt`, `vp lint` and `vp pack` read.** A scratch project showed a hand-wrapped paragraph failing `vp fmt --check` and a type error failing `vp lint` with `craftz()`, and both passing without it. A probe showed a plugin's `pack` banner and types taking effect in `vp pack` too. The hook wins over the repository's own config without a word, so `craftz()` fails a config that sets a value differently.
- **publint and the types belong in the pack.** `vp pack` runs publint with `publint: { strict: true }` and fails the build on a problem, so it needs no step of its own, only `publint` installed. Types had come from three places: `typescript` installed, or `isolatedDeclarations` in `tsconfig.json`, which the editor then applied to tests and config, and which `vp check` doesn't check. `dts: { generator: "oxc" }` applies it only to what's packed, and a missing type still fails the pack. Each package wrote the same lines in its pack block, until `craftz()` set them.
- **The editor formatted with a different oxfmt from `check`.** User settings pointed VS Code's oxc extension at a global oxfmt and a deleted config. Without them, the extension finds `vite-plus` and runs `vp fmt --lsp`. So there's no global oxfmt to pin, and each repository commits the `.vscode/` settings Vite+ writes.
- **With no `fmt` block, `vp fmt` prints "No config found".** An empty `fmt: {}` keeps the defaults and drops the notice.
- **A framework needs steps around `vp check`.** SvelteKit generates types that `svelte-kit sync` and `wrangler types` write first, and oxlint doesn't type-check `.svelte` files, so `svelte-check` runs after. The rules hold `check` to running `vp check`, not to being only that.
- **`verify` ran its steps one after another.** Each repository chained them with `&&`, so craftz's `verify` took 23 seconds, the sum of its steps, while its tests alone took 15. `vp run` runs `package.json` scripts side by side, as the `dependsOn` of one task in `vite.config.ts`, and a script's `&&` steps run in order within it. craftz's `verify` takes 17 seconds that way. A task needs a command, so `all` runs `true`, and `vp run` takes one task, so the scripts can't be named on its line. Three things came up. A `build` beside the tests broke a test that packs, since `pnpm pack` builds too, so craftz left `build` to its tests, until they packed from a build in a folder of their own. A warm cache replayed a step and failed a test that passed without it, which stayed unexplained, so the cache is off. And a step that writes can't run beside steps that read, so the outline left `verify` for `pr` and `gone`. A plugin could have added the task, but then `verify` would run what no file shows, so the task and the scripts stay in the repository's files.
- **Five repositories moved `verify` to `all` by hand.** A task in `vite.config.ts` can't share a name with a script, and only a task has a `dependsOn`. So a step that waits for another became a task under a name of its own, like pagez's `budget` after `build`, while a script that waits for nothing, like markz's `size`, went straight into `all`. prose's tests packed into `dist/` too, as craftz's do, so they pack into a folder of their own, with a copy of `package.json`, where the command reads its version. Before moving a step beside the others, read what it reads and writes on disk.
- **The report listed moves that no pull request made.** The run for 0.11.0 listed nine repositories under Moved, but the five left by hand got no pull request and stayed on 0.10.0. A report says what reached a repository, so a repository left by hand or failed lists only what's left. The fix had also given up on all five, though most of each move was mechanical, so it now does that part and the check names each step that's left.
- **Vite's default browsers were three years old.** `baseline-widely-available` is a list frozen at each Vite major, and Vite+ 1.3.0 has May 2025's: Chrome 111 and Safari 16.4, from 2023. base built to it, so its CSS nesting was flattened, while prose used popover, which needs iOS 18.3. Usage data showed only the iPhones that a new iOS drops are held back for long, so the rules set a floor per engine instead, in [Browsers](rules.md#browsers), worked out from MDN's browser-compat-data. It has each Samsung Internet release's Chromium and which Firefox is the ESR, and it was a release ahead of caniuse. caniuse's usage counts Android Chrome as one version and leaves out in-app browsers, so read it next to a source that counts those.
- **A package can extend its own tsconfig by name.** TypeScript resolves `@amitkaps/craftz/tsconfig.json` through the package's own `exports`, inside craftz too, so craftz's `tsconfig.json` extends it as every other repository's does, and `toolchain-types` has no case for craftz. Read a tsconfig by parsing it. The regular expressions found an option even in a comment, and couldn't tell which file set it.
- **A config read by its lines found keys that weren't there.** The rules read `vite.config.ts` with regular expressions, so a key in a comment counted, any `target: [...]` read as `build.target`, and a fix placed its block by the file's last line. Vite+ exports oxc's parser as `parseSync`, so the rules parse the config instead, in about a millisecond, and read only what's written as a literal. Loading the config as Vite does took half a second to a second, and runs its plugins. `vite-plus` itself takes a quarter of a second to load, so it's required on the first parse, and `pr` and `status` never pay for it.
- **What a repository's config read from craftz didn't show in its files.** `craftz()` set `fmt`, `lint` and a package's pack and browsers, and every `tsconfig.json` extended craftz's. So a release could change a repository's format, lint, types and build with no diff in it, and uninstalling craftz broke the build. Each config writes them out now, and the plugin is gone. Parsing made that cheap to check, since `check` reads each value where it sits, and the fix writes in one that differs without touching the rest of the block.

## Cloudflare

- **An internal site leaks through `workers.dev`.** Access covers a domain, not a Worker, so its `workers.dev` address and preview URLs serve the site to anyone. Every site turns both off in its config.
- **A setting that marked a site internal kept a private repository from having a public one.** Turning off `workers.dev` was how a config said it was internal, so a private repository's public site couldn't turn it off, and the public sites served on `workers.dev` and preview URLs nobody used. Every site turns both off now, and Access alone says whether a site is internal. A fact that's true of every site can't also mark some of them.
- **`private` in `package.json` already meant something.** It means "not on npm", and a tool can be `private` with a public site. Whether a site is internal comes from the repository's visibility, and its config says so where it takes effect.
- **Each Worker had its own compatibility date.** They were set the day each config was written, and the static sites never needed them to differ. The date is the workerd build that cf installs, so it moves with the betas, and it's never newer than the local runtime, which falls back to its own date and warns. Since 2026-08-04 the date also turns on Node.js compatibility, so no flag is needed. Written into each config, every `pnpm bump` that moved cf meant a fix that edited the date's line in each repository. So `site()` set it from the craftz a repository installed, and a config that set the date failed. That hid the date, and broke the deploy without craftz, so the date is written out again, and the fix moves it.
- **A dependency can ask for more Node than the floor.** cf beta.20 needs Node 26.12.0, while the floor was `>=26`, so moving cf alone would have let a repository say it runs on a Node cf refuses. Read a new version's `engines` when moving it, and move the floor with it.
- **The Vite plugin's `beta` tag isn't the build to take.** It can point at a build inside pnpm's wait, or at one whose `@cloudflare/config` no cf build has yet. Take the newest build past the wait that depends on the same `@cloudflare/config` as cf, read with `pnpm view <package>@<version> dependencies`.
- **A Worker config read from craftz broke without it.** `site()` filled in a static site's date and addresses, so `cloudflare.config.ts` imported craftz, and the deploy read values no file showed. The config is now cf's own format, with no import, and `craftz deploy` and the rules parse it rather than run it. cf has no field for the folder, so `assets.directory` stays in the config until cf adds one. Only an app's `wrangler.toml` is still read with regular expressions, since nothing installed parses TOML.
- **The Git integration deploys whether or not CI passed.** A build command of `pnpm run verify` fails first, so nothing deploys.
- **The Worker's settings can be written with cf.** cf's config has no field for the build commands, but `cf builds triggers` sets them and `NODE_VERSION`, so `craftz settings` writes them. Set `NODE_VERSION` on every Worker, since the integration reads pnpm's version from the repository but not Node's. It installs dependencies itself, so the build command doesn't.
- **Reconnecting a repository resets the Worker's build settings.** The commands, `NODE_VERSION`, the cache and previews went back to the defaults. Run `craftz settings` after any reconnect.
- **cf has no command to rename a Worker, but the dashboard does.** Settings → General → Name keeps its ID, Git connection and domains. Rename it there first, then in the config, since a new name in the config deploys a new Worker.
- **The config lists the Worker's domains.** prose's domain was once set only in the dashboard, where a deploy could drop it. Change one in the dashboard and the config together, so a deploy can't put the old one back.
- **cf needs `CLOUDFLARE_ACCOUNT_ID` when the login has several accounts.** craftz's commands pick the account named like the GitHub owner. A `pnpm ship` by hand doesn't, so set it there.
- **A prose site reaches cf through Vite.** cf's config has no assets folder, so cf couldn't deploy one that Vite didn't build. Vite takes `.prose` as its `publicDir`, and the plugin with `assetsOnly` writes it out for `cf deploy --prebuilt`.
- **The plugin already did what an empty entry did.** Vite won't build without an entry, so one site gave it an empty one. The plugin does the same when there's no `index.html`. Read a workaround's reason against the tool's current release before copying it.
- **A plugin only the build uses was loaded by every check.** Vite+ loads the whole config for `fmt`, `lint` and `vp check`, so a site's check imported Cloudflare's plugin and miniflare, and took twice a package's time. base's imported SvelteKit and its adapter. The plan waited for Vite+ to tell a check from a build, and it already did: its `lazyPlugins()` skips the plugins while it reads a config for a block of it. prose's `vp check` went from 4.7 to 2.2 seconds, and base's from 5.1 to 2.4. Wrap any plugin only a build or a test needs. Before waiting on a tool for a feature, read its docs for it.
- **A deploy can be tested before there's anywhere to deploy to.** `cf deploy --prebuilt --dry-run` reads the Build Output and stops before the upload, so craftz's site was checked before its Worker existed. Run it after `vp build` on any site whose deploy changes, before the first real one.
- **cf can't deploy SvelteKit yet.** The adapter doesn't write cf's Build Output, so base stays on wrangler, with `wrangler.toml`, since prose reads comments in TOML but not JSONC.
- **Void deploys a folder in one command, on more machinery than a folder needs.** It installs 304 packages, a database toolkit and its own state. Tried as of void 1.1.11 and left, since Vite and the plugin already do the job.
- **A static site installed a runtime it never ran.** cf, Cloudflare's plugin and wrangler each bring workerd, 133 MB of a site's 373 MB install, to run code a static site doesn't have. Their deploy of a folder is five calls to Cloudflare's API: a manifest of hashes, the files Cloudflare doesn't have, the Worker with no code, its domains and its addresses. `craftz deploy` makes them with `fetch`, so a site installs Vite+ and craftz, about 140 MB. Weigh a tool by what the repository runs of it, not by what it's for.
- **craftz installed cf for one version number.** cf brought workerd and miniflare, 343 MB of a 502 MB install, and craftz ran none of it. It read workerd's version for the Workers' date, and ran cf's commands, which already fell back to pnpm's fetch. npm says which workerd the reference's cf depends on, so [src/workerd.json](../src/workerd.json) keeps that, and craftz's install fell to 162 MB. A cf on the PATH at the reference's version runs, as `gh` does, so how it was installed doesn't matter.
- **A package's prose site can't build before the first commit.** `prose build` publishes a commit, so `new` commits, then runs `verify`, where it ran `verify` first.
- **A test that runs the CLI three times timed out under load.** craftz check takes over a second in a child process, and the full suite runs new's verify beside it, so the hold test passed alone and failed one run in two at five seconds. A test that starts the CLI more than once gets its own timeout.
- **A build machine is slower than a laptop.** A timing test in markz passed locally and in CI, then stopped a deploy on Cloudflare's machine, since the build command is `verify`. A timing test takes the best of several runs, after warming up, on inputs big enough to measure.

## GitHub

- **Five repositories protected `main` four ways.** A ruleset is one JSON document, so it lives here and `craftz settings` applies it everywhere.
- **GitHub shows anyone a public repository's branch rules, but not its merge settings.** Reading the settings needs `gh`'s login, so `craftz settings --check` runs on a laptop, not in CI.
- **GitHub's rate limit looked like drift.** Logged out, 60 requests an hour turned every rule red with HTTP 403. Use `gh`'s login when it can, and say a check the limit stopped wasn't made.
- **A read straight after a write can be the old answer.** `new --push` wrote craftz-test's branch rules and labels, then reported each as still off. They were there a minute later. GitHub answered the read-back from before the write. A read-back that drifts is tried again a few times before it's reported, so "still off" means the write didn't take.
- **Dependabot duplicated what moves from here.** It can't move the Vite+ override with Vite+, and every npm pull request it opened was closed. Versions move in the reference first, so there's no Dependabot, and `github-ci` drifts on a `dependabot.yml`.
- **A pull request behind `main` waited forever.** Two open at once in one repository, and whichever merged second sat blocked, since `main` requires an up-to-date branch and auto-merge doesn't update one. Turning that rule off would let two changes that pass alone break `main` together, and a merge queue needs an organisation. So `pnpm pr --wait` and align's wait update a branch that falls behind.
- **The wait was in the session, not in CI.** Over 60 pull requests here, CI took about a minute, and only two were ever open together, so the up-to-date rule cost one run. But `pnpm pr` stopped on a new title while the branch's pull request was open, so an agent ran `--wait` and sat through CI before starting the next change. A pull request merges in a minute or two, sooner than the next change is written. So `pr` returns once it's pushed, and a new title waits only for a merge that hasn't happened. Turning off the up-to-date rule was ruled out again, since an always-green `main` is worth more than the reruns.
- **Auto-merge can wait minutes after the checks pass.** Across four repositories, pull requests with every check green and nothing behind sat 6 to 12 minutes before GitHub merged them. A wait that sees a pull request ready now merges it itself. The rules still decide what merges, so this loosens nothing.
- **A pull request read as behind its own merge.** The first `--wait` after that change failed on a pull request that had merged. For about a second, the squash commit was on `main` and the pull request was still open, so GitHub called it behind, and updating it failed with nothing to update. A failed update now means asking again, and the next look sees it merged.
- **Two runs started together, and the cancelled one blocked the merge.** `pnpm pr` opens a pull request with its label, and gh adds the label in a second request, so GitHub starts a label run for `opened` and another for `labeled`. The `opened` event carries no label, and the concurrency group cancelled that run. GitHub counted the cancelled run against the required check, so the pull request stayed blocked until it was run again. Giving the label check a workflow of its own didn't help, since both runs were in it. Now `label.yml` reads the labels from GitHub when it runs, and no run cancels another. Read what a check judges when it runs, not from the event that started it.
- **A skipped check passes.** The label check was to move to a job in CI that ran on a label change while `ci` skipped. But a check belongs to a commit, and GitHub takes its latest run. A label added after `ci` failed would have left a skipped `ci`, which counts as passing, and the pull request would merge. A workflow of its own runs only the label check on a label change, and `ci` keeps its last real result. When a required check could skip, ask what it reports for the commit.
- **A squash merge hides what it took.** `pnpm pr` counted a branch's commits ahead of `main` to tell if anything was new. A squash merge writes new commits on `main`, so the branch's own stay ahead, and a second run pushed a pull request with nothing in it. Whether a branch adds anything is a question about trees, not commits: merge it onto `main`, and see if `main` changes.
- **`pnpm pr` pushed into whatever branch it was on.** An agent ran it twice, and the second change merged inside the first pull request, under its title. Another ran it on a branch whose pull request had squash-merged, and the new pull request carried the merged commits again. The branch's pull request decides now, and a title that isn't its own starts a new branch or stops.
- **`gone` stopped at a branch a worktree had checked out.** An agent's worktree kept a merged branch, git refused to delete it even with `--force`, and the error ended the run, so the branches after it stayed too. `gone` now removes that worktree first, without `--force`, so one with changes is kept with its branch, and the rest are still deleted.
- **A step nobody runs is a step for a command to take.** AGENTS.md said `pnpm gone` deletes the merged branches after a merge, and no agent ran it, since an agent opens a pull request and moves on before it merges. Ten repositories held thirteen merged branches. Some `gone` couldn't have found anyway: three never tracked GitHub, one came from `gh pr checkout`, and one GitHub kept after its merge. `pr` now runs `gone` first, and `gone` also deletes a branch whose last commit is a merged pull request's or is on `main`.
- **An agent runs a step tied to a moment, not one tied to a session.** `AGENTS.md` said to end a session with `--wait`, to land on `main`. But a session that auto-compacts never ends, so agents edited on a merged branch or a stale `main`, and session hooks fire too rarely to help. `AGENTS.md` now says to run `pnpm gone` before starting a change, and `gone` pulls `main` too, so the step does what the line says.
- **An editor under an agent waits where nobody sees it.** `craftz release` without `--notes` opened `vi` for the summary, and an agent's run sat there with no output and no pull request, which read as a release workflow that never started. `release` now stops without a terminal and asks for `--notes`. A command an agent runs never waits on input it can't give.
- **Two files with one name read as one thing.** The notes' config sat at `.github/release.yml`, GitHub's default, beside the release workflow at `.github/workflows/release.yml`, and the pair read as a duplicate. Only the config's path was GitHub's choice, and the API that writes the notes takes another. It's `.github/notes.yml` now. Renaming the workflow was ruled out, since npm's trusted publisher names its file in every package, by hand.
- **Replacing a tool drops what it did quietly.** `craftz deploy` replaced `cf deploy` with the same calls to Cloudflare's API, but sent each bucket of files once, where cf tries again. markz's site changes every page in each build, so it sends many buckets, and one `10013`, Cloudflare's unknown error, failed a deploy. A bucket is now tried five times. When a command replaces a tool, list what the tool does on failure too.
- **A list in the code fell behind the repositories.** align read six names from a list in the code, which kept the old repository after it had moved and never gained craftz-test, and adding one took a pull request here. GitHub's topics are the list now: writing a repository's settings adds `craftz`, archiving it takes it off, and only public repositories are read, so the list can't name a private one. Search takes a few seconds to see a new topic, so a repository just set up may be missing from a run made right after.
- **A lesson named a private repository.** It reached the docs, a commit and a pull request before it was caught, and GitHub keeps the old text. `AGENTS.md` now says never to name one, anywhere this repository reaches.
- **A private repository runs CI on half the machine.** GitHub gives a public repository's job four cores and a private one's two, and the logs show it, as `2 threads` beside `4 threads`. So a private app's `verify` took 33 seconds, its build and tests sharing two cores. The budget is still the same, since the time a person waits is what it's for, but read a private repository's time knowing it.

## npm and releases

- **Three copies of one release workflow had drifted.** Each staged differently, and only one had labels or a size budget. The workflow names no package now, so one file is copied everywhere and checked word for word.
- **A summary in an annotated tag can't be reviewed.** It's the description of the pull request that bumps the version, reviewed like any change, and the workflow reads it from the merged commit.
- **Pushing a tag by hand was the step that went wrong.** A branch named `v0.4.0` made the tag's push ambiguous. The workflow tags the merged commit itself, the bump branch is `release-X.Y.Z`, and npm's 2FA approval is the one step by hand. `craftz release` opens the pull request with the owner's login, since GitHub runs no CI on one a workflow's token opens.
- **A label checked at release time is checked too late.** prose's v0.5.0 notes were all Other until the labels were added by hand. A package's `ci` fails without exactly one label, and every `AGENTS.md` says which to pass to `pnpm pr`, which stops without one.
- **Supporting an older Node than we build on took a workaround.** pnpm won't run on a Node older than `devEngines`, so testing on 24 meant switching Node after the install. With no users on 24, `engines` asks for the Node it's built on. If a package gains users on an older one, that job is how to test it.
- **Bundling our own packages removes the release order.** A package with markz as a dev dependency puts it in `dist/`, so it depends on nothing at install and releases at any time.

## Docs

- **How Markdown wraps was left to each writer.** At oxfmt's default `proseWrap: "preserve"`, most repositories put a paragraph on one line and markz hand-wrapped at about 100 characters, and nothing flagged the mix. `"never"` waited on markz, since a `{@section}` line with text beneath it is part of the paragraph to plain Markdown, and the reformat joined it in. markz 0.5.0 warns about an element line without blank lines around it, and once every repository had fixed its lines, `toolchain-wrap` turned `"never"` on everywhere. It also stops padding a table wider than the print width, as Prettier does, so the rules' docs table lost its columns' alignment in the source, while narrower tables kept theirs. Before changing a formatter setting that reflows text, check what the reflow joins.
- **The rules are a doc, so they go in `docs/`.** They first moved into the reference folder, next to the files they describe. But prose publishes `docs/` in the site's nav, and a doc anywhere else is left out of it, as prose's usage and markz's grammar show. So the rules are `docs/rules.md`, and `reference/` holds only files a repository has. A doc's name is a choice, and "standard" had been one. "Rules" matches the command that prints them.
- **The reference has to pass the checks too.** The old repository's files became [reference/](../reference/README.md), and `prose check` reads them like any other file, since it has no way to leave a folder out. Their links pointed at that repository's layout, and `AGENTS.md` carried its own section. So links now point at craftz's files, and `AGENTS.md` keeps only the sections every repository shares. Keep what's in `reference/` true where it stands, rather than marking it unchecked.
- **Copied rules drift.** The `@prose` rules had started to differ across four `AGENTS.md` files. Each links to the one copy in prose's docs, and the section is checked word for word.
- **A pointer to rules fires only at the step it names.** `AGENTS.md` said to read the prose rules before writing prose, so an agent deleting code never read them, and "Kept current" is a rule about changing code. It now names that step too. A pointer outlives a summarized session where the rules it points to don't, so name every step a rule applies to.
- **A command's summary became its manual, and the copies drifted.** `cli.ts`'s prose described every subcommand, as `AGENTS.md`, usage, the help and each subcommand's own file did. Five said what `status` reads, and two had missed the audience it added. The summary now names each subcommand and links the file that explains it, as prose's command does, and `AGENTS.md` says only what `status` is for. `prose style` read each sentence as fine, since the fault was across files.
- **A copy of the rules goes stale where it's copied.** Development docs described settings the rules had moved past, and READMEs pinned versions. `development.md` links the rules for anything shared, and a plan lists only its own repository's steps.
- **A doc that copied the versions went stale.** The beta table in `development.md` listed each pin and its status on a date, and align kept its own list of the betas. Both fell behind the code. The rules are docs, and a check holds the code to them, so a doc says what's allowed and why, never the value. `versions-beta` names the betas once, the check fails any other pre-release, and `package.json` alone has the builds.
- **Each repository kept its plan its own way.** All six had the same headings, but done work was a section per release in two, a section per milestone in two, and a line per capability in prose. The milestone ones grew to over 2,000 words, while prose's stayed short, since a line is rewritten rather than added. GitHub's release notes already hold what each release did, and `gh release view` reads them. So a plan opens with what's next, and says what works now, one line per thing.
- **A plan tracks its own repository.** craftz's plan ticked each repository as it moved to a release, which the rules say a plan doesn't do. The moves are each repository's own pull requests, in its own plan, and what a release asks of them is in its notes. craftz's plan says what craftz does next.
- **prose builds the last commit, not the working tree.** A new doc is missing from the site until it's committed. Commit before building to see it, as the Cloudflare build does.
- **prose's check found only text nobody meant to be right.** Its warnings were on test corpora and fixtures that are wrong on purpose. Mark those `linguist-vendored`, which prose skips.
- **`prose style` was right about length and wrong about lists.** On its first run here it made 68 suggestions. Every long summary, long sentence, parenthetical and semicolon was worth fixing, and splitting a long summary always read better. A colon that joins two clauses was too. But 24 of its 42 colons only introduced a list, which is fine. prose 0.7.1 took that advice and leaves a list's colon alone. Take the length suggestions as they come.
- **A page from the build fits in prose as a doc with a hole in it.** A dashboard was a doc with an empty `{@section}` for each table that a script filled after `prose build`, so it had prose's bar and styles, with no renderer of its own. A section's id can't be a heading's, and markz warns `duplicate-id` when it is.
- **A copy of a tool's layout breaks when the tool moves.** The dashboard sized itself with prose's `--docked`, which prose renamed. Keep only what's a page's own, and take the rest, like the status colours, from prose's tokens.
- **A hand-written `.html` page ships its comments.** Vite doesn't strip them, so such a page carries no prose.

## The rules

- **A rule said in two places drifts in one.** The standard, as the rules were called then, said a rule in words and the survey said it again in a check's label, and the two disagreed. A rule now has an id, like markz's grammar gives its side rules. The rules state it once, as a list item that opens with the id, and `src/rules.ts` has only the check and the fix. - **A version nobody looks at drifts.** Checking versions found what the setup checks missed: prose asked for Node 24, had no Vite+ override, and two repositories were behind on markz. Every shared version is checked now.

- **Try a standard in every repository before writing it.** Each repository's tsconfig looked like it had reasons of its own: a DOM `lib` here, `resolveJsonModule` there. Setting one tsconfig in each and running its check showed which reasons were real. Only SvelteKit's were, and two constructors that Node can't run as they're written.
- **A value that moves with craftz belongs in a call, not a file.** What every config shares, like `fmt`, `lint`, a package's pack and a Worker's date, comes from `craftz()` and `worker()`, from the version a repository installs. A new craftz changes them with no edit, and the check only looks for the call.
- **`craftz()` sets nothing that's the repository's to say.** It set `publicDir` to `.prose` for any static site with no `index.html`, a guess that held while every such site was a prose site. A site built by Sitez had its folder replaced, and its build failed on a font it couldn't find. The folder is the site's to name, so a prose site writes `.prose`, and the rule checks that it does.
- **"Once the repositories move" is a rule that hasn't been written.** The rules said every site's `ship` would run `craftz deploy` once the repositories moved to craftz, but nothing checked it, so `new` still wrote `cf deploy --prebuilt`, and the first test repository came out on the old command. A sentence about the end state is a rule waiting for its id. Write the check before the release that the repositories move to.
- **A move that changes the name leaves the old one behind.** Every moved repository passed `craftz check`, and four still sent readers to the old repository's site, in their README, development notes and plans. No rule looked for the old name. `docs-old-name` looked, until every repository had moved and was clean, and then it went, since a rule with nothing left to find is only a cost. When a move renames something, a rule that finds the old name ships with it, and goes once the move is done.
- **A hold kept in craftz cost a release.** craftz kept each repository's holds by its name, which made sense while craftz checked the others from outside. Once each repository checked itself against the craftz it installs, adding or dropping a hold meant changing craftz, releasing it, and upgrading the repository. A hold is the repository's own now, in its `package.json`, and craftz only says which rules a tool can block. When a check moves into the repository, move what tunes it there too.
- **"Equal to the reference" made a package wait for the one it builds on.** prose builds on markz, so it needs markz's next release before craftz does. A check that wanted the reference's version exactly failed prose until craftz moved and released. A caret range didn't help, because the check compared strings, and below 1.0 `^0.6.0` doesn't reach 0.7.0 anyway. Our own packages are at least the reference's now, still exact. A third-party tool still waits for craftz, since craftz decides when everyone moves.
- **What every agent reads is `AGENTS.md`, so the standard goes there.** prose tried shipping its rules as a pnpm agent skill. It took an approval in each workspace, a folder per agent and a fallback for agents that don't load skills, to deliver what one line in `AGENTS.md` does. The shared sections now say when to run each command, and `@outline.md` imports the repository's outline, which `verify` writes.

## Checks and fixes

- **A repository checks itself, so no sweep does.** The rules were checked only when align or drift ran from craftz, so a pull request elsewhere could drift and still merge. A move to a new release was checked against craftz's `main`, not the release. `craftz check` reads only files and needs no login, so it runs in every `verify`, against the craftz each repository installs. drift then checked the same files a second time, against rules not yet released, and reported drift no repository could fix, so it went. What it read that needs a login went to the commands that already had one: `craftz settings --check`, `craftz status` for a site's audience, and `pnpm align --local` for every repository at once.
- **A folder's name isn't its repository.** Holds were found by the folder's name, so `craftz check` in a worktree of a held repository missed its holds and failed, while `craftz settings` in the same folder found the repository from `origin`. Two ways to name one thing will disagree somewhere. A folder is the repository its `origin` names, and only a folder with no `origin` goes by its own name.
- **One catch hid five drifts behind a wrong reason.** A check on a private repository's folder said its settings weren't checked, since it "isn't on GitHub". GitHub had it. Its Worker wasn't connected to the repository, so Cloudflare's build settings answered 404, and the catch around both checks took that error for GitHub's, dropping four merge settings with it. Catch only the error you expect, beside the call that throws it.
- **A copy is proven by the same output.** The checks came from the repository that kept the rules, so the test was running both and comparing. On repositories that are in line, both print the same ticks, which shows little. So a clone of markz was made to drift on purpose, and both printed the same findings. Do the same when moving a check, so a change in behaviour shows up as a difference.
- **A copied file keeps what nothing reads.** The reference's `package.json` came over as the old repository's, with its name and its own scripts, which no rule reads. It looked like part of the rules. Now it holds only what a rule or `new` reads, and its name says it's the reference.
- **A fix that sets the reference's value can run on every repository.** align had its own code to move the shared versions. Each version rule's fix now does it, reading the reference, and changes nothing in a repository already in line, so every fix runs without checking first.
- **A generator and a fixer write the same files twice.** `new` built the editor settings, the shared `AGENTS.md` sections, the release files and more, and the fixes wrote them again. `new` now writes only what's a repository's own and runs the fixes for the rest, so a rule with a fix needs nothing added to `new`.
- **A fix that rewrites a file undoes the formatter.** The first `craftz fix` on a repository in line changed `.vscode/extensions.json`. The fix wrote the JSON it parsed with `JSON.stringify`, which puts the formatter's one-line array on four lines. Now a JSON file is written only when its value changes. To prove a fix is idempotent, run `craftz fix` twice on each repository's `main` from `git archive`, since a local checkout can be behind and look like drift.
- **A fix that edits a file by its lines depends on its layout.** CI's Label step was edited in place, anchored on lines every repository had, and a workflow laid out otherwise was left alone to drift. Taking that step out took its `@prose` comment, which in one repository was the only one in the file, so `prose check` failed after the fix. Running align on a real repository before a release found it, where the tests' CI still had its header. A file every repository has the same is now written whole from the reference and checked word for word, so no fix guesses at a layout.
- **A fix that edits a config missed every real one.** `toolchain-craftz` took out `fmt` and `lint` only when they were exactly what `craftz()` sets, but each moved repository had its own `ignorePatterns` in them, so every one was trimmed by hand. Its plugins went in on one line, too, which `vp check` failed where they were one to a line. And it found the plugin's values through its own copy, written as patterns, so a change to the plugin would have left it taking out the old values. Write a fix against a real repository's file, not the reference's, and test it on one. Once every repository had moved, the trimming went, and the fix only adds the call.
- **One line for every tool's findings.** craftz printed drift as `id: text` with a `see:` line, a held rule over two lines, and notes in a third shape, while prose printed `prose: warning: path:line: code: …`. An agent reading both learned two formats. Every finding now takes markz's line, `craftz: warning: versions-markz: …`, and a held one ends with `; held:` on the same line. align picks out what's left by hand by that prefix, so a format change there is a change to align too.
- **Keep what edits code apart from the rules.** The fixes that edit a repository's own code were spread through the rules, each reading and writing its file. Now they're in one file, as functions from text to text, so the edits that depend on a file's layout can be read together and tested without a folder. An edit belongs there only where `craftz()` can't do the job, like adding itself, and a fix that moved repositories off an old layout goes once they're past it.

- **Bringing six repositories in line was a script nobody had written.** Each move to a new tool took six hand-made pull requests, and the check only listed them. `pnpm align` makes the edits, runs `verify` and opens the pull requests.
- **A sweep runs the version it moves to.** align fixed every repository from craftz's checkout, against a reference it had just moved, while each repository's `verify` ran the craftz it installed, which still wanted the old versions. align now moves each repository to the latest craftz on npm and runs that version's `craftz fix`. `craftz upgrade` does the same in one repository, running the fix as its own process, so it's the new version's. align takes those steps from craftz's source, since a repository on an older craftz doesn't have `upgrade` yet. But the others install the reference from npm, so what the run moved in craftz reached nobody until the next release, and the docs said the opposite. `pnpm bump` now moves the reference before a release, and `pnpm align` takes the release to the others after it.

A deduped package's dependencies are now read from where they were printed. A line that says each dependency is one package was the sign, and the test now holds a deduped tree.

Every repository reached 0.7.0 with it still there. An audit of @prose found it, since the condition was written where it could be read. Write the condition for removing something next to it, and check it when releasing.

Now it names the rule by id, and `craftz rules <id>` prints the rule from the version installed, so the rule read is the one that was checked. It works like `prose rules`, so an agent that knows one knows the other.

## Tests

- **A generator copies the rules, so it's tested against them.** The tests run `craftz check` and `verify` on what `new` writes. Its first run showed oxfmt formats arrays differently from `JSON.stringify`, so `new` runs `fix` rather than copying oxfmt's rules.
- **The tests run the packed command.** A test from source can't show what the package leaves out, which is how `new` failing to start was found. Before a release, unpack `pnpm pack`'s tarball and run the command from there, with no `node_modules`.
- **A test can't install the version it's releasing.** The 0.1.1 release failed CI. `new` writes craftz's own version, `^0.1.1`, and the test ran `pnpm install` on it, a version npm wouldn't have until the release merged. The test now overrides the dependency with this checkout, so it tests the craftz being released. It passed locally and failed again in CI, since the checkout's exports are its build, and only the local copy had a stale one. So the test builds it first. A test of what a release writes uses the release, not the registry.
- **A file craftz writes whole can't be edited to set up a test.** The tests installed the packed craftz by adding an override to the new repository's `pnpm-workspace.yaml`. Once that file had to be the reference's word for word, `craftz check` failed on the test's own edit. The test now puts the file back after the install, since pnpm only reads it then.
- **A check runs on what will be committed.** The first dry run of the move failed prose's `verify`. Its lexer test lexes every file `git ls-files` lists, and align ran `verify` before staging, so git still listed the files the fix had deleted. `pnpm pr` commits first, so it never hit this. align now stages before `verify`, so a check sees what the pull request will hold.
- **A slow check is measured before it's waited on.** `verify` took two and a half minutes, two of them the tests. Timing each part found two causes. Every test file that read the rules spent 12 seconds importing MDN's browser data, since a JSON import is turned into a module first, and `require` parses it natively in a fraction of that. And the five repositories `new`'s test writes ran one after another, though each has a folder of its own. `verify` takes under a minute now. When something's slow, time its parts before guessing.
- **Time a slow test before cutting it.** craftz's tests took 32 seconds, nearly all of it five generated repositories running `fix` and `verify`. Timing each step found two costs that weren't the test's. `new` wrote JSON that oxfmt reformats, so every run needed a `fix` first, and `new` now formats what it writes. And a site's config imports Cloudflare's plugin, a second each time any `vp` command loads it, which every site repository pays on every `vp check`. Cutting the five repositories to one would have hidden both.
- **A shape is verified for what it runs, not for its flags.** `new`'s test ran `verify` on five repositories, one for each mix of `--package`, `--site`, `--private` and `--internal`, at about 15 seconds each. Only two build differently. A package with a site packs and builds prose's site, and a static site builds with Vite from `index.html`. The rest run a part of what those do, and being private or internal only changes files the survey reads. So all five are checked against the survey, which takes milliseconds, and only those two run `verify`, with the static site private and internal. The tests went from 21 to 15 seconds. When a test repeats an expensive step per case, list what each case runs that the others don't.
- **Work at a module's top level runs for every command.** Every `craftz` command took about 190 ms, and 50 ms of that went to parsing the rules doc three times. Three constants in `rules.ts` and `survey.ts` parsed it when their module loaded, and `cli.ts` imports both, so `gone` paid for rules it never read. The doc is now parsed on first use, once a run, and a command that needs no rule takes about 140 ms. Profile a command that does nothing to find what every command pays.
- **Splitting a slow test file only helps when a core is idle.** `vp test` already runs files side by side, one to a core. Splitting markz's slowest files to bring its `verify` under the budget saved 3 of 30 seconds, since its tests kept every core busy, so the split was dropped. A split pays when one long file runs alone at the end, and costs a little import time otherwise. So time `verify` before and after a split, and keep it only when the time falls.

## Before a release

- **A word-for-word file changes for everyone at once, so it changes before the release.** The `AGENTS.md` sections and the release files still linked the old repository's page, since they're shared word for word. They changed here before craftz's first release, so the first version a repository installs already points at craftz. A change later would need a release of its own, and a round of pull requests in every repository. Before a release, grep the reference for links to anywhere that isn't craftz.
- **What every repository changes for goes in before the release.** `pr.ts` and `gone.ts` were to become commands after the repositories moved. That would have changed the reference in a second release, and sent every repository a second round of pull requests. So they became `craftz pr` and `craftz gone` first. Before a release, ask what the next one would change in every repository, and move it into this one.
- **A rule that's missed is found by the next thing to use it.** 0.1.0 went out without a rule that a repository depends on craftz, so `new` still wrote the `fmt` and `lint` blocks, and a repository could follow the rules without ever installing them. The question "why isn't `new` in this release?" found it. Before a release, start a repository with `new` and read what it writes against what the release is for.
- **A release's notes come from a run, not a plan.** 0.4.0's notes listed what the plan said each repository would change by hand. align then failed six sites on `cloudflare-worker`, which had no fix, since only `craftz new` wrote `worker()`, and no site was started by it. align could only move a repository to what npm already had, so nothing ran a release before it shipped. `pnpm align --candidate` now moves every repository to this checkout, packed, and what each leaves by hand is what the notes say.
- **A rule without a fix waits on every repository.** `cloudflare-worker` said a config without `worker()` is written by hand, and every config was the same shape, which a fix moves in a line. Before a rule ships without a fix, look at what the repositories have.
- **pagez was the first repository `new` started.** CI passed on the first push. Run it without `--push` first, to read the files before they reach GitHub. A package's first push changes `package.json`, so the release workflow stops for a package npm doesn't have yet.
